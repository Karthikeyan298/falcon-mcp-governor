Introduction

Falcon is an open-source MCP (Model Context Protocol) governance gateway. Instead of letting AI agents connect directly to your MCP servers — Jira, email, databases, Kubernetes, and anything else — they connect to Falcon first. Every tool call passes through a policy engine, a trust registry, and an audit trail before (or instead of) reaching the real upstream server.

🛡️ Policy Enforcement

YAML rules decide allow, deny, or require approval for every agent × server × tool combination.

✅ Human Approvals

Flag sensitive tools for mandatory admin review before they execute.

🔔 Anomaly Detection

Automatic alerts for denial spikes, call rate floods, new tool attempts, and approval floods.

📋 Audit Trail

Append-only log of every decision: who, what, when, and why.

🔑 Trust Registry

Per-tool signature verification — revoked tools are blocked before policy is even consulted.

🔍 Parameter Rules

Inspect tool call arguments — block emails to external domains, protect production namespaces, etc.

Architecture

Falcon sits between your AI agents and your MCP servers. Agents authenticate with an API key and speak the MCP streamable-HTTP protocol. Falcon intercepts, evaluates policy, then either proxies to the real server or returns a block/pending response.

Quick Start

Option A — Docker Compose (recommended)

# Clone the repo
git clone https://github.com/your-org/falcon-mcp-governor.git
cd falcon-mcp-governor

# Build and start
docker compose up -d --build

# Get the one-time admin password (first boot only)
docker compose logs backend | grep -A3 "created default admin"

Open http://localhost:4200 and log in with admin + the password from the log.

⚠️
The one-time bootstrap password is printed once at first startup. Copy it immediately. If you lose it, delete the database (docker compose down -v) to regenerate.

Option B — Local development

# Backend
cd backend
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000

# Frontend (separate terminal)
cd ui/mcp-governance-ui
npm install
npm start    # → http://localhost:4200

Authentication & Users

Session-based login (UI / REST API)

Every /api/* route — except /api/auth/* — requires a valid session cookie (falcon_session). Sessions are HttpOnly, valid for 24 hours, and stored server-side in the sessions table. 

# Login
curl -c cookies.txt -X POST http://localhost:8000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"your-password"}'

# Use session cookie for subsequent requests
curl -b cookies.txt http://localhost:8000/api/agents

Changing your password

Any logged-in user can change their own password via Account → Change password in the UI, or: 

POST /api/auth/password
{"current_password": "old", "new_password": "newpass123"}

Changing the password invalidates all other active sessions for that user.

User management (admin only)

Admins can create additional users from the Users tab. The response includes a one-time temp_password — copy it immediately. Users should change it on first login.

RolePermissions
adminFull access including user management, approvals, and all admin actions
userAccess to all non-admin endpoints (audit, gateway, agents, servers, policies)
✅
Create a personal admin account and deactivate the bootstrap admin account for better auditability. Every action is logged under the authenticated username.

Agents

An agent in Falcon is an identity representing an AI agent (a LangChain app, a LangGraph pipeline, a CrewAI crew, etc.). Agents authenticate to the gateway using an API key, and policy is evaluated based on the resolved agent name — not anything the client self-reports.

Registering an agent

Go to Agents tab → Register agent, or:

POST /api/agents
{
  "name": "story-creator",
  "owner": "alice",
  "environment": "Production",
  "status": "Active"
}

The response includes a one-time api_key:

{
  "name": "story-creator",
  "owner": "alice",
  "environment": "Production",
  "tools_allowed": 5,
  "status": "Active",
  "api_key": "mcp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
}
🚨
Copy the API key immediately. Falcon only stores its hash — the raw key is never retrievable again. If you lose it, delete the agent and register a new one.

Tools allowed

The Tools allowed count shown on the Agents page is computed dynamically from the current deployed policy — it reflects exactly how many (server, tool) combinations are not denied for that agent under the live policy. It updates automatically when you deploy a new policy.

Suspending an agent

Toggle an agent's status from Active to Suspended via the Agents tab or POST /api/agents/{name}/toggle. A suspended agent is immediately blocked at authentication — even with a valid API key, gateway requests return 401 Unauthorized.

Deleting an agent

Delete via the Agents tab or DELETE /api/agents/{name}. The agent's API key becomes permanently invalid. Audit records referencing the agent are retained.

MCP Servers

An MCP server is an upstream tool provider — an email server, database, Jira, Kubernetes API, or any service that speaks the MCP streamable-HTTP protocol. You register it with Falcon so that agents can connect through the gateway instead of directly.

Registering a server

Servers tab → Add server, or:

POST /api/servers
{
  "slug": "email-server",
  "name": "Email MCP",
  "endpoint": "http://localhost:8002/mcp",
  "trust": "Trusted"
}
FieldDescription
slugURL-safe identifier used in gateway routes (/mcp/{slug}) and policy YAML
nameHuman-readable display name
endpointFull HTTP/HTTPS URL of the upstream MCP server's streamable-HTTP endpoint
trustTrusted or Needs review — applied to all tools discovered from this server

Syncing tools

Click Sync on a server (or POST /api/servers/{slug}/sync) to discover its live tool list. Sync:

  • Replaces Falcon's local tool list with what the server actually reports
  • Upserts a trust record per tool (Verified for Trusted servers, Needs approval otherwise)
  • Fills in a conservative default policy action for newly-discovered tools not already covered: Low risk → allow, Medium/High risk → deny
  • Preserves rules you have already set — no existing policy is overwritten
ℹ️
Re-sync whenever the upstream server adds or removes tools. New tools won't appear in Falcon's policy evaluation or audit trail until a sync has run.

Trust levels

StatusEffect
VerifiedTool is trusted; policy evaluation proceeds normally
Needs approvalTool is blocked regardless of policy action — must be manually promoted
RevokedTool is permanently blocked; cannot be called even if policy says allow

Trust status is checked before policy. A tool with action: allow in policy is still denied if its trust status is Revoked or Needs approval.

Policy Engine

Policy is a single YAML document — the source of truth for what every agent is allowed to do. It is evaluated at call time against the live deployed version; a policy deploy takes effect immediately for all subsequent calls.

Policy structure

servers:                        # default rules — apply to every agent
  email-server:
    tools:
      send_email:
        action: allow
        param_rules:             # optional per-argument checks
          - param: recipient
            not_endswith: "@company.com"
            decision: deny
            reason: External recipient blocked
      delete_email:
        action: deny
      "*":                         # wildcard — fallback for unlisted tools
        action: deny

  database:
    tools:
      read_record:
        action: allow
      delete_record:
        action: require_approval  # held for human review

agent_overrides:                 # optional, keyed by agent name
  hr-agent:
    servers:
      email-server:
        tools:
          send_email:
            action: deny          # overrides the default for this agent only

Policy actions

ActionEffect
allow Tool call is proxied to the upstream MCP server and the result returned to the agent
deny Tool call is blocked. Agent receives an MCP error response with the denial reason
require_approval Tool call is blocked, a pending approval record is created, and an admin must approve or deny it before it executes

Evaluation order

For a given call (agent, server, tool), the engine checks in this order:

  1. Trust registry — if the tool's status is Revoked or Needs approval, deny immediately
  2. Policy lookup — finds the most-specific matching rule:
    1. Agent-specific exact tool match
    2. Agent-specific wildcard ("*")
    3. Default exact tool match
    4. Default wildcard ("*")
    5. Default deny (no match)
  3. Parameter rules — if the matched config has param_rules, evaluate each against the call arguments. A firing deny rule wins over the base action.

Deploying a policy

Edit the YAML in the Policies tab (or stage changes with the rule builders) then click Deploy. The policy is validated before saving — an invalid YAML or missing servers key returns a 422 error. A deploy is logged in the audit trail under agent control-plane.

Rule Builder

The rule builder provides a form-driven way to add or update policy rules without editing YAML directly. It stages changes into the YAML editor — nothing is saved until you click Deploy.

Adding an allow/deny/require_approval rule

1
Go to the Policies page.
2
In the Rule builder panel, select: Applies to (agent scope — blank = all agents), Server, Tool (or * for all), and Action (allow, deny, or require approval).
3
Click Add rule to YAML. The YAML editor updates with the merged rule — review it.
4
Click Deploy to persist and activate the policy.
⚠️
"Add rule to YAML" only stages the change in the text editor. It does not take effect until you click Deploy.

Parameter Rules

Parameter rules let you inspect tool call arguments and make decisions based on their values — for example, blocking emails to external domains, or denying operations in a production namespace.

Param rule builder

The Param rule builder panel on the Policies page adds param rules without writing YAML manually:

1
Select the agent scope, server, and tool the rule applies to.
2
Enter the Parameter name (must match the tool's argument name exactly).
3
Choose an Operator and enter a Value.
4
Choose a Decision (deny, allow, or require_approval) and an optional reason.
5
Click Add param rule to YAML, review, then Deploy.

Operators

OperatorMatches when…Example
equalsValue exactly equals the targetnamespace equals production
not_equalsValue does not equal the targetenvironment not_equals staging
endswithValue ends with the target stringrecipient endswith @company.com
not_endswithValue does not end with the targetrecipient not_endswith @company.com

YAML representation

send_email:
  action: allow
  param_rules:
    - param: recipient
      not_endswith: "@company.com"
      decision: deny
      reason: External recipient blocked
    - param: recipient
      endswith: "@vip-partner.com"
      decision: require_approval
      reason: VIP partner email requires admin sign-off

Rules in param_rules are evaluated in order. A deny rule wins over any other decision, including the base action. A missing or non-string parameter value never triggers a rule (the rule is skipped).

Tool Policy Matrix

The Tool policy matrix panel on the Policies page gives a tabular view of every tool and its policy status. Crucially, it evaluates the policy per-agent — so selecting an agent shows exactly what that agent is and isn't allowed to do.

Using the filters

FilterEffect

The count in the top-right of the panel updates as you filter.

Status badges

Gateway Proxy

The real MCP gateway lives at /mcp/{server-slug}. Agents connect here instead of directly to the upstream MCP server. The gateway speaks the MCP streamable-HTTP protocol.

Authentication

All MCP requests must include the agent's API key:

X-Agent-Key: mcp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

An optional header attributes calls to a specific human user in the audit log:

X-Agent-User: alice

Session flow

1
Initialize — POST /mcp/{slug} with method: "initialize". Falcon resolves the agent from X-Agent-Key, creates a session with the upstream server, and returns a mcp-session-id header.
2
List tools — method: "tools/list". Tools that would be denied for this agent are removed from the response — the agent never sees them.
3
Call a tool — method: "tools/call". Falcon evaluates policy. On allow, proxies the call and returns the real result. On deny or require_approval, returns an MCP error result with isError: true.
4
Close — DELETE /mcp/{slug} with the session ID header.

Complete example

# 1. Initialize
curl -X POST http://localhost:8000/mcp/email-server \
  -H "X-Agent-Key: mcp_abc123" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"my-agent","version":"1.0"}}}'

# Response includes: mcp-session-id header

# 2. Call a tool
curl -X POST http://localhost:8000/mcp/email-server \
  -H "X-Agent-Key: mcp_abc123" \
  -H "mcp-session-id: <session-id-from-step-1>" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"send_email","arguments":{"recipient":"alice@company.com","subject":"Hello","body":"Hi"}}}'

Gateway test page (no real agent needed)

The Gateway tab in the UI lets you simulate a tool call through the full policy engine without needing a running agent or upstream server. Pick an agent, server, and tool; fill in arguments; and submit. The result shows the policy decision and reason, and the call is written to the audit trail — useful for testing policy changes before deploying them.

Approvals Workflow

When a tool has action: require_approval in policy, every call to that tool from an agent is held — the agent receives a blocked response, and the call is queued for human review. An admin can then approve or deny it from the Approvals page.

How it works end-to-end

1
Agent calls a tool marked require_approval. The gateway logs a Pending audit entry, creates an approval record, and returns a blocked MCP error to the agent: "This operation requires human approval before it can be executed."
2
Pending badge appears on the Approvals nav item, showing the count of unreviewed requests. The page auto-refreshes every 8 seconds.
3
An admin navigates to Approvals and reviews the request — agent identity, tool, arguments, and requestor are all shown.
4a
Approve — policy is re-evaluated against the live policy at approval time (a deny rule added after the request was made is still enforced). If still allowed, Falcon connects directly to the upstream MCP server and executes the tool, logging the result as Allowed. The agent does not need to retry.
4b
Deny — the approval record is marked denied, a Denied audit entry is written, and anomaly detection runs on the denial (contributing toward repeated-denial alerts).

Approval statuses

StatusMeaning
pendingAwaiting admin decision
approvedAdmin approved; execution in progress or complete
executedTool was successfully called on the upstream server after approval
deniedAdmin explicitly rejected the request
ℹ️
Approval does not bypass policy — the live policy is re-evaluated at execution time. If a new deny rule was added between the approval request and the admin's decision, the call is still blocked and logged as Denied.

Setting a tool to require approval

Via the rule builder: select server, tool, action = Require approval, then deploy. Or directly in YAML:

delete_record:
  action: require_approval

Alerts & Anomaly Detection

Falcon continuously monitors the audit trail for suspicious patterns and automatically creates alerts when anomalies are detected. Alerts appear on the Alerts page, and an unacknowledged count badge appears in the nav.

Alert types

TypeTriggers when…Default threshold
repeated_denials An agent accumulates too many denied tool calls in a time window — possible policy misconfiguration or probing 5 denials in 10 minutes
high_call_rate An agent makes an unusually large number of tool calls in a short window — possible runaway loop 30 calls in 1 minute
new_tool_attempt An agent calls a tool it has never called before (first-ever appearance in audit for that agent × server × tool) First occurrence (no threshold)
approval_flood An agent generates an unusually large number of approval requests in a short window 5 pending decisions in 10 minutes

Alert deduplication

Falcon will not create a new alert of the same type for the same agent while an unacknowledged alert of that type already exists (except new_tool_attempt, which deduplicates on the agent + server + tool combination). This prevents alert storms from a single ongoing issue.

Configuring alert rules

On the Alerts page, click Configure rules to adjust thresholds, time windows, severity, and enable/disable individual alert types. Changes take effect immediately for subsequent calls.

SettingDescription
enabledToggle an alert type on or off entirely
thresholdNumber of events that must occur before the alert fires
window_minutesTime window over which events are counted (rolling)
severityVisual severity level: low, medium, or high

Acknowledging alerts

Click Acknowledge on an alert to mark it reviewed. Acknowledged alerts remain visible (dimmed) for audit purposes. Acknowledging an alert resets the deduplication window — if the condition persists, a new alert can fire again.

When detection runs

Anomaly detection runs synchronously after every tool call decision — both through the real MCP gateway (/mcp/{slug}) and through the UI Gateway test page (/api/gateway/invoke). Admin denials of approval requests also run detection, contributing toward the repeated_denials count.

Audit Trail

The Audit tab shows an append-only log of every policy decision and gateway action. Records are never modified or deleted — the trail is tamper-evident by design.

Troubleshooting

SymptomLikely cause & fix
Login works in curl but not in the browser CORS mismatch — set FALCON_UI_ORIGINS to exactly match the origin (scheme+host+port) the UI is served from
Agent gets 401 at gateway Missing or wrong X-Agent-Key, or the agent is Suspended. Check the agent status in the Agents tab.
Tool call returns 502 Policy allowed the call but the upstream MCP server is unreachable. This is a downstream connectivity problem, not a policy denial — check the audit trail for Allowed to confirm.
New tool isn't appearing Sync the server again. Tools are only known to Falcon after a successful sync.
Rule builder change did nothing "Add rule to YAML" only stages the change in the editor. Click Deploy to activate it.
Alerts aren't firing despite denials Check the configured thresholds and time windows on the Alerts page. Denials must occur within the window to count. Also ensure the alert type is enabled.
Approval request not appearing on the Approvals page The policy action must be exactly require_approval (not deny). Verify in the deployed YAML on the Policies page, and check the audit trail for a Pending entry.
Lost the bootstrap admin password No reset flow exists. Either log in as another admin account, or wipe the database (docker compose down -v) to regenerate. All data is lost.
Database errors after upgrading Schema migrations run automatically on startup (additive only). For unexpected errors, delete backend/data/control_plane.db and restart to reinitialize from scratch.
